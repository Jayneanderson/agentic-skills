# openspec-setup-brownfield

Inicializa as definições OpenSpec em um projeto **brownfield**.

Ao final, o projeto terá:
- `openspec/config.yaml` — contexto do serviço e regras por artefato
- `openspec/project.md` — domínio, funcionalidades, arquitetura, decisões, débitos técnicos, stack
- `openspec/specs/<capability>/spec.md` — uma spec por capability já implementada
- `.gitignore` atualizado para não versionar arquivos de skill

---

## Como usar

/openspec-setup-brownfield [caminho-do-projeto]

Se nenhum caminho for informado, usar o diretório atual.

---

## Execução

É importante que todas as etapas sejam realizadas em ordem (exceto as fases 1 e 2 que podem ser feitas em paralelo) porque a fase 3 depende das respostas da fase 2.

### Fase 0 - Ignorar arquivos de skill no versionamento do git

Antes de qualquer outra coisa, garanta que os arquivos de skill não sejam versionados.

Localize o `.gitignore` na raiz do projeto (crie-o se não existir) e adicione ao final:

    # OpenSpec (generated by openspec init; do not version)
    .opencode/commands/opsx-*.md
    .opencode/skills/openspec-*/

Não peça confirmação para este passo, visto que é sempre seguro e não afeta código de produção.

### Fase 1 - Exploração silenciosa do projeto

Antes de fazer qualquer pergunta ou criar qualquer arquivo, explore o projeto da seguinte forma:

1. **Estrutura de diretórios** para stack (linguagem, framework, banco de dados e afins), arquitetura em camadas (exemplo: Clean Architecture, Hexagonal, MVC), abordagem de projeto (exemplo: DDD, TDD), monoreposiório ou serviço isolado;
2. **Documentação existente** como README, docs ou quaisquer outros arquivos .md presentes na raiz do projeto ou nos diretrórios em si. Isso inclui docs de migração, ADRs, decision logs e afins. Leia para ter contexto;
3. **Entrypoints HTTP e assíncronos** como rotas, controllers, consumers e publishers de fila. Mapeie o verbo/path (caminho), handler e usa case cada um chama;
4. **Domínio** — identifique entidades, agregados, value objects, enums;
5. **Integrações externas** — HTTP clients, producers/consumers de mensageria, clientes de banco, webhooks e demais integrações;
6. **Testes** — nomes dos testes revelam comportamento esperado. Leia os casos de teste para entender regras de negócio implícitas e explícitas;
7. **Infraestrutura** como banco de dados, tópicos/filas, variáveis de ambiente relevantes, controladores, serviços, cache, feature flags e pontos relacionados;

Ao final desta fase, você deve responder mesmo que parcialmente:
- Qual é o propósito do serviço?
- Quais são as entidades principais do domínio?
- Quais capabilities existem (use cases implementados)?
- Quem chama este serviço e quem este serviço chama?

---

### Fase 2 — Perguntas ao usuário

Nesta fase, você deve perguntar **apenas o que o código não revelou** ou casos que tenham ficado confusos após leitura do código. Após isso, apresente o que você entendeu e peça confirmação/complemento de informação a partir dessa estrutura em markdown:

    ## O que entendi do projeto

    [resumo em bullets do que a exploração revelou]

    ## O que preciso que você me diga

    1. **Propósito** (se não ficou claro): Em uma frase, qual o papel deste serviço
       no ecossistema? Ex: "fonte da verdade de X", "orquestrador de Y", "gateway para Z".

    2. **Arquitetura atual vs. alvo** (se houver migração em andamento):
       Há um estado "hoje" e um estado "target" que devem ser documentados separadamente?
       Se sim, descreva brevemente o target.

    3. **Consumers/callers**: Quem chama este serviço? (se não identificável pelo código)
       Ex: user-service, app mobile, cron job...

    4. **Decisões de arquitetura já tomadas**: Há decisões relevantes que não estão
       no código? Ex: "escolhemos não fazer X por causa de Y", "usamos Z em vez de W".

    5. **Débitos técnicos conhecidos**: Há dívidas técnicas que a equipe reconhece?
       Ex: versão de runtime antiga, modelo de dados incompleto, retrocompatibilidade.

    6. **Capabilities planejadas** (opcional): Há funcionalidades em backlog ou planejadas
       que devem aparecer no project.md como 📋 Planejada ou 📌 Backlog?

#### Observações

- Não avance para a Fase 3 sem as respostas da Fase 2, pois elas são essenciais. Se o usuário pedir para avançar mesmo assim, assuma apenas o que a exploração revelou e documente as lacunas nos arquivos gerados a partir de uma seção chamada "a definir".

### Fase 3 - Rascunho antes de gravar

**Apresente o rascunho do config.yaml e do project.md antes de criar arquivos.** Aguarde confirmação explícita ("ok", "pode gravar", "certo", "pode", "vai lá", "pode ir") antes de escrever qualquer coisa.

#### Estrutura do config.yaml

    schema: spec-driven

    context: |
      # Descreva o serviço em 1-2 frases (propósito e responsabilidade principal,
      # sem detalhes de implementação).

      ## Arquitetura atual
      # Descreva apenas o que existe hoje e é conhecido.
      # Fluxo: quem chama → o que o serviço faz → quem recebe a resposta/evento.
      # Inclua os limites de responsabilidade: o que o serviço NÃO faz.

      ## Arquitetura alvo
      # Omitir se não houver migração ou mudança arquitetural em andamento.
      # Descreva somente o estado desejado já decidido.

      ## Domínio
      # Entidades, agregados, value objects, eventos e regras de negócio.
      # Um conceito por linha.
      # Não descreva classes ou detalhes de implementação.

      ## Arquitetura do serviço
      # Camadas, módulos, responsabilidades, path aliases, mensageria,
      # persistência e integrações externas.

      ## Dependências e integrações
      # Sistemas que o serviço consome e sistemas que dependem dele.
      # Indique o propósito de cada dependência.

      ## Convenções
      # Idioma do código e documentação, commits, nomenclatura,
      # estrutura de pastas e estrutura do OpenSpec.

      ## Restrições
      # Decisões ou limitações que não devem ser violadas.

    rules:
      general:
        - O código e os artefatos existentes são a fonte de verdade sobre o estado atual.
        - Diferencie fatos observados de decisões futuras.
        - Nunca descreva a arquitetura alvo como se já estivesse implementada.
        - Não invente componentes, integrações, regras ou dependências.
        - Quando uma informação não for conhecida, sinalize a lacuna em vez de inferi-la.
        - Documente somente informações relevantes para compreender, modificar ou integrar com o serviço.
        - Prefira descrições curtas e concretas.

      proposal:
        - Estruture o conteúdo em listas; um conceito por bullet.
        - Explique o problema, objetivo e mudança proposta.
        - Inclua impacto nos consumidores e nas integrações externas.
        - Registre decisões de negócio e decisões arquiteturais relevantes.
        - Não descreva detalhes de implementação; esses pertencem ao design.md.
        - Não apresente decisões ainda não tomadas como fatos.

      specs:
        - Main specs (openspec/specs/): use headers ## Purpose e ## Requirements.
        - Requisitos devem usar ### Requirement: e expressar comportamento obrigatório usando SHALL ou MUST.
        - Cenários devem usar #### Scenario: e descrever QUANDO/ENTÃO.
        - Escreva requisitos e cenários em português.
        - Cada requisito deve descrever comportamento observável, não implementação.
        - Referencie conceitos do domínio quando aplicável.
        - Delta specs (openspec/changes/): use ## ADDED/MODIFIED/REMOVED/RENAMED Requirements.
        - Nunca copie deltas crus para openspec/specs/; consolide-os na main spec.
        - Estruture o conteúdo em listas; um conceito por bullet quando apropriado.

      design:
        - Descreva como a solução será implementada para atender aos requisitos.
        - Especifique como dados fluem entre camadas.
        - Detalhe mudanças e impactos no banco, mensageria e integrações HTTP.
        - Explicite decisões técnicas relevantes e seus trade-offs quando existirem.
        - Não repita requisitos ou cenários já definidos nas specs.

      tasks:
        - Quebre o trabalho em unidades pequenas e verificáveis.
        - Agrupe por camada (domain, use-cases, external, presentation) quando isso melhorar a organização.
        - Inclua testes na mesma fase do código que eles validam.
        - Descreva o entregável/objetivo, não os passos de implementação.
        - Evite tarefas que apenas repetem requisitos ou decisões do design.

### Fase 4 — Exploração de capabilities (modo explore)

Após gravar `config.yaml` e `project.md`, explore o código para identificar as
capabilities implementadas antes de escrever as specs.

O objetivo desta fase é descobrir **o que o serviço oferece**, definir as
fronteiras das capabilities e identificar ambiguidades que precisam de
confirmação do usuário.

Não escreva ou altere specs nesta fase.

#### Identificação

Mapeie apenas capabilities que representem comportamento observável ou uma
responsabilidade relevante do serviço.

Não trate como capability:
- funções ou classes internas sem comportamento observável;
- detalhes de implementação;
- operações puramente técnicas, como logging, configuração ou mapeamento;
- CRUD interno que não represente uma capacidade do domínio, salvo quando
  isso for relevante para o contrato do serviço.

Apresente ao usuário:

    ---

    ## Capabilities identificadas

    - **<nome-sugerido>** — <descrição em 1 linha>
      - Entrada: <HTTP endpoint, evento, subscription, comando ou outro gatilho>
      - Comportamento: <o que a capability faz em termos de negócio>
      - Saída: <HTTP response, evento, escrita/alteração no banco ou outro efeito>
      - Dependências: <serviços ou sistemas externos relevantes>
      - Status: <implementada / parcialmente implementada>
      - Dúvidas: <pontos que precisam de confirmação, se houver>

    ---

#### Agrupamento e fronteiras

Depois de identificar as capabilities, avalie se elas devem compartilhar uma
mesma spec ou possuir specs independentes.

Considere:
- mesmo comportamento de negócio com transportes diferentes;
- mesmo fluxo com variações de entrada ou saída;
- capabilities que compartilham regras de negócio;
- capabilities que possuem regras, invariantes ou critérios de aceitação diferentes;
- dependências ou contratos externos diferentes;
- necessidade de evolução independente.

Não crie uma spec por endpoint automaticamente. A fronteira da spec deve ser
determinada pelo comportamento que precisa ser especificado, não pelo
transporte utilizado.

Apresente ao usuário as decisões que exigem confirmação:

## Perguntas antes de escrever as specs

Faça perguntas somente quando houver ambiguidade relevante.

Exemplos:

- **Capabilities X e Y** têm o mesmo comportamento de negócio, mas são expostas
  por HTTP e mensageria. Devem compartilhar uma spec?
- **Capability Z** possui os sub-casos A e B. Eles compartilham as mesmas regras
  e invariantes ou devem ser especificados separadamente?
- **Capability W** parece parcialmente implementada. O comportamento atual deve
  ser documentado como spec ou existe um comportamento esperado diferente?
- **Capabilities A e B** usam o mesmo domínio, mas possuem consumidores e
  contratos externos diferentes. Devem evoluir de forma independente?
- <outras dúvidas específicas identificadas durante a exploração>

Se não houver ambiguidades relevantes, informe que as capabilities e suas
fronteiras estão claras e prossiga para a escrita das specs.

#### Regras

- Baseie as capabilities no comportamento encontrado no código, não nos nomes
  de arquivos, classes ou endpoints.
- Não invente capabilities que não possam ser identificadas no projeto.
- Não trate detalhes de implementação como comportamento do sistema.
- Diferencie comportamento observado de comportamento desejado.
- Preserve o vocabulário do domínio existente.
- Prefira nomes orientados à capacidade do negócio em vez de nomes técnicos.
- Uma capability pode possuir múltiplos pontos de entrada ou saída.
- Uma capability não precisa corresponder a um único endpoint, handler,
  consumer ou classe.
- Não escreva specs até que as ambiguidades relevantes de escopo tenham sido
  resolvidas.

### Fase 5 — Escrita das specs (formato canônico de main spec)

 Para cada capability confirmada, crie:

 `openspec/specs/<capability>/spec.md`

 As main specs representam o **comportamento atualmente suportado pelo sistema**.\
 Em um projeto brownfield, elas devem ser derivadas principalmente do código,\
 testes, contratos externos e comportamento observável.

 **Importante:** arquivos em `openspec/specs/` são **main specs** validadas pelo\
 CLI com `openspec validate --specs`. NÃO use o formato de delta\
 (`## ADDED Requirements`, `## MODIFIED Requirements`, etc.) em main specs.

 O formato de delta é exclusivo de:

 `openspec/changes/<change>/specs/`

 #### Estrutura obrigatória

```
# <capability> Specification

## Purpose
[1-3 frases em português; mínimo ~50 caracteres.
Explique o propósito da capability no ecossistema.]

## Requirements

### Requirement: <nome curto>
O sistema SHALL [comportamento observável em português].

#### Scenario: <nome descritivo>
- **QUANDO** [condição]
- **ENTÃO** [resultado]
- **E** [efeito adicional, opcional]
```

 #### Critérios para uma boa spec brownfield

 - Documente o comportamento **atualmente implementado e observável**.
- Extraia requisitos a partir do código, testes, contratos e integrações existentes.
- Não invente regras de negócio, validações, estados ou comportamentos que não\
   possam ser sustentados por evidências no projeto.
- Não transforme automaticamente todo comportamento encontrado no código em\
   requisito de negócio. Diferencie comportamento intencional de comportamento\
   aparentemente acidental.
- Quando houver evidência conflitante entre código, testes e contratos, não\
   escolha silenciosamente uma fonte. Registre a ambiguidade e marque o ponto\
   como `_a definir_` quando necessário.
- Cada `### Requirement:` MUST possuir pelo menos um `#### Scenario:`.
- Cada cenário MUST possuir pelo menos `QUANDO` e `ENTÃO`.
- Documente cenários de sucesso e de erro relevantes ao comportamento da\
   capability.
- Inclua efeitos observáveis relevantes, como persistência, publicação de\
   eventos ou chamadas a integrações externas.
- Não descreva implementação. Não mencione classes, métodos, funções,\
   arquivos ou frameworks como parte do comportamento especificado.
- Organize requirements por comportamento ou conceito de domínio, e não por\
   arquivo, classe, endpoint ou camada técnica.
- Uma capability pode ter múltiplos pontos de entrada, desde que representem\
   o mesmo comportamento especificado.
- Preserve o vocabulário do domínio já utilizado no projeto.
- Use `_a definir_` somente quando a informação for necessária para compreender\
   o comportamento, mas não puder ser determinada de forma confiável a partir\
   das evidências disponíveis.
- Não use `_a definir_` para esconder falta de exploração. Antes de marcar algo\
   como indefinido, procure evidências no código, testes, configurações e\
   contratos relacionados.
- `_a definir_` é um marcador documental e nunca deve aparecer como valor,\
   estado, resposta ou comportamento do sistema.
- Não altere o comportamento existente durante esta fase. Se o comportamento\
   atual estiver incorreto ou precisar mudar, registre isso como uma mudança\
   futura em `openspec/changes/`.
- A main spec deve refletir o comportamento atual, mesmo quando esse\
   comportamento for tecnicamente questionável ou aparentemente inadequado.
- Não "corrija" a especificação para representar o comportamento esperado sem\
   evidência de que essa seja uma decisão já adotada.
- Comportamentos identificados como incorretos, obsoletos ou candidatos a\
   mudança devem ser registrados como observações ou mudanças futuras, não\
   silenciosamente alterados na main spec.
- Evite duplicar requirements entre capabilities. Quando uma regra pertence\
   claramente a outra capability, referencie-a em vez de copiá-la.

 #### Validação da spec

 Antes de considerar uma main spec concluída:

 1. Verifique cada requirement contra o código que implementa a capability.
2. Verifique cada cenário contra os testes existentes, quando houver.
3. Verifique contratos HTTP, eventos e integrações externas relevantes.
4. Identifique comportamentos observados que contradizem outros requisitos.
5. Identifique afirmações que não possuem evidência suficiente.
6. Marque lacunas reais como `_a definir_`.
7. Remova detalhes de implementação que tenham vazado para a spec.
8. Verifique se cada `Requirement` possui pelo menos um `Scenario`.
9. Verifique se cada cenário possui `QUANDO` e `ENTÃO`.
10. Execute `openspec validate --specs --strict`.

 #### Regra de fonte de verdade

 Em caso de divergência, considere as evidências na seguinte ordem:

 1. Comportamento observável em produção, quando conhecido.
2. Contratos externos e integrações estabelecidas.
3. Testes existentes que validam comportamento.
4. Código atualmente executado.
5. Configurações e documentação existente.

 Quando as evidências não permitirem determinar o comportamento com segurança,\
 não invente uma resposta. Registre a lacuna como `_a definir_` e, quando\
 necessário, solicite confirmação ao usuário.

 > A ordem acima não significa que testes ou código sejam ignorados quando não\
>  houver conhecimento do comportamento em produção. Ela serve para orientar a\
>  resolução de conflitos e evitar que uma única fonte seja tratada\
>  automaticamente como verdade absoluta.

```

#### Regras a adicionar em `config.yaml`

    rules:
      specs:
        - Main specs (openspec/specs/): use headers ## Purpose e ## Requirements.
        - Requisitos devem usar ### Requirement: com SHALL ou MUST no corpo.
        - Cenários devem usar #### Scenario: com bullets QUANDO/ENTÃO.
        - Escreva requisitos e cenários em português.
        - Main specs devem documentar comportamento atual e observável.
        - Derive requisitos de código, testes, contratos e integrações existentes.
        - Não invente comportamento ou regras de negócio.
        - Diferencie comportamento observado de comportamento desejado.
        - Não descreva detalhes de implementação.
        - Organize requirements por comportamento ou conceito de domínio.
        - Use `_a definir_` somente para lacunas documentais reais.
        - `_a definir_` nunca representa um valor ou comportamento do sistema.

        - Nunca copie deltas crus para openspec/specs/.
        - Após criar ou sincronizar main specs, execute `openspec validate --specs --strict`.
:::
```
---

### Fase 6 — Validação das main specs

Antes de concluir o setup, valide **todas** as specs principais:

    openspec validate --specs --strict

Se houver falhas, corrija estrutura (Purpose/Requirements ausentes, requirement sem SHALL,
cenário faltando) antes de seguir. Não confundir com `openspec validate <change>` — isso
valida apenas deltas de uma change ativa.

---

### Fase 7 — Atualização do project.md

Após criar e validar todas as specs, volte ao project.md e preencha a coluna `Spec / Change`
na tabela de Funcionalidades com o caminho relativo de cada spec criada.

---

## O que esta skill NÃO faz

- Não cria design.md, tasks.md ou proposal.md — esses artefatos pertencem a changes
  (mudanças futuras). Use /openspec-new-change ou /openspec-ff-change para isso.
- Não faz suposições sobre arquitetura alvo sem input do usuário.
- Não cria specs para funcionalidades planejadas — apenas para o que está implementado.
